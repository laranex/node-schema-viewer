# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Security

- `serve` binds only to loopback (`127.0.0.0/8`, `::1`, `localhost`) and refuses any other `--host` with exit code 2. `--unsafe-allow-remote` binds it anyway (never by default, no configuration key) and prints a warning on every start: no authentication, no TLS, anyone who can reach the address can read the schema, and the Host check is not access control. Remote access is documented only behind an authenticated HTTPS reverse proxy or tunnel, with the server on loopback.
- The drift gate's GitHub Actions example builds the document in the job (from the database with a read-only role, or from the schema modules) instead of gating a committed one, and uploads only the gate report, with a short retention; `docs/build.md` says build outputs are sensitive and belong in `.gitignore`. The repository ignores `/schema-viewer.json` and `/schema-viewer.html`.
- CI (`.github/workflows/tests.yml`): lint, typecheck and the release guard; the suite on Node.js 22.13.0, 22, 24 and 26 with PostgreSQL, MySQL and MariaDB service containers; the container isolation tests with an image built from the packed package, on host Node.js 22 and 24.

### Changed

- `laranex-schema-viewer-ui` is the exact npm version 0.3.0 (the vendored tarball and the packaging test's and container image's `overrides` are gone), with the normative gate specification, `gateDocument`, `validateGateReport`, the shared producer exports (`expandComparisonRequests`, `coverageGaps`, `coverageGapText`, `scopeCovered`, `DIFFERENCE_FIELDS`, `validateSeverityOverrides`, `comparisonDiagnostics`, `storeComparisons`, `spellScope`) and their conformance cases.
- `compare` and `check` call the shared producer exports instead of their own copies: request expansion, coverage-gap wording, the `comparison_incomplete` diagnostic and storing comparisons come from `laranex-schema-viewer-ui`, and overrides in `package.json` are checked by `validateSeverityOverrides`. Behaviour changes: a `*` target that matches no schema is now an error (`Requested comparison … matches no schema.`, exit 1) instead of comparing nothing; every request error (unknown connection, `*` without inspected schemas or without a match, the same request listed more than once) uses the contract's message (`Requested comparison A → B …`) and `compare` reports all of them; override errors use the contract's wording after the entry's location (`… comparisons[0] overrides[1].field must be one of comment for objectType table`), and two overrides for one `(objectType, change, field)` are now an error. Scopes are spelled with the shared `spellScope`.
- **laranex-schema 2.0 only** (`laranex-schema-viewer-ui` 0.3.0). Snapshots are read as 2.x (later minors leniently) and written as strictly validated, canonical 2.0; a 1.x document is refused with one clear error (`Unsupported laranex-schema version "1.0"; this reader supports 2.x. Rebuild the snapshot with a producer that writes laranex-schema 2.0 …`). Nothing converts 1.x.
- Database introspection writes 2.0: canonical driver names (`postgresql` instead of `pgsql`, `mysql`, `mariadb`, `sqlite`), indexes with `parts` and `backs` only (no `Index.columns` or `Index.primary`), diagnostics with rule-based ids, and the new `comparisons`, `migrations` and `inferredAssociations` arrays (empty for now). The catalog readers fill a normalized internal schema model that does not use the document's field names, and one serializer writes it, builds the links with the shared graph builder and validates strictly; `merge` composes serialized documents. The database conformance documents are python-schema-viewer's own 2.0 output, recorded from the same synthetic databases, and the Node.js documents equal them. Security is unchanged: separate worker, Permission Model flags, URL on stdin, verified read-only sessions, privilege checks and scrubbing.
- The extraction worker's result must be exactly a strictly valid 2.0 `declared` document.
- Containers are named `nsv-extract-…` (python-schema-viewer uses `lsv-extract-…`), and a timed-out container is waited for until the runtime has really removed it; the error names it.
- `serve` serves the 0.3.0 viewer from the dependency (manifest-only, the same Content-Security-Policy) and refuses a viewer build whose manifest does not declare contract major 2.

### Fixed

- `check` rejects a comparison configured twice, as the contract requires of producers: exit 2 with `Requested comparison A → B is listed more than once.` on stderr and no report, before the snapshot is read, instead of passing the duplicate to the gate, which dropped it silently. A comparison named twice on the command line is rejected the same way, now also when the snapshot is invalid or unreadable. `compare` already failed on both (exit 1). The behaviour and messages match python-schema-viewer's.
- Atomic writes (`compare --write`, `check --output`, `init`) work under the Node.js Permission Model: Node.js 22.23+, 24 and 26 refuse `fsync` there even inside `--allow-fs-write`, so `ERR_ACCESS_DENIED` from `fsync` is tolerated only when the process runs under the Permission Model (the file is still written to a temporary file and renamed; it is not flushed first). Every other `fsync` error still fails the write, and a failed write removes its temporary file with `unlink` (which, unlike `rm`, needs no read access) and leaves an existing file as it was. The extraction and introspection workers are unchanged. See `docs/security.md`.

### Added

- `build [--source declared|database]`, a port of python-schema-viewer's `build` with its options, messages and exit codes where they apply (0 written, 1 error with nothing written, 2 usage). `declared` imports the configured schema modules only in the isolated extraction worker (process isolation on Node.js 26, container isolation required on 22 and 24, never weaker) through an ORM adapter; `database` reads the live catalogs read-only, one introspection worker per connection, with URLs read only from the environment variables the configuration or `--database NAME=ENV_VAR`/`--database-url-env` names (default `LARANEX_SCHEMA_DATABASE_URL`), passed only to the introspection worker on stdin, and stores configured or `--compare` comparisons. The document is strictly validated and written atomically; a failed build leaves the previous file. The extraction worker may also read `laranex-schema-viewer-ui`, which the adapters serialize with, wherever it is installed. `--source combined` exits 2 with "not available yet". See `docs/build.md`.
- The Drizzle ORM adapter (`drizzle-orm` 0.36 to 0.45, an optional peer dependency loaded from the project; tested with 0.36.4, 0.38.4, 0.40.1, 0.44.7 and 0.45.4), for `pg-core`, `mysql-core` and `sqlite-core` through Drizzle's metadata API (`is`/`Table`, `getTableConfig`, `getTableName`, `getSQLType`, the dialects' SQL rendering, `extractTablesRelationalConfig`/`normalizeRelation`): tables with `pgSchema`/`mysqlSchema` schemas, columns (types, nullability, SQL and literal defaults, `$defaultFn` as an ORM default, identity, serial and auto-increment, generated columns, enums), composite primary keys, composite and cross-schema foreign keys with actions, unique constraints, indexes (expressions, order, nulls, operator classes, methods, predicates, PostgreSQL and MySQL options in `dialectOptions`), checks, each table as a model, and `relations()` as read-only ORM relationships (one/many with keys, cardinality and inverses), kept separate from foreign keys; foreign keys without a relation become the contract's inferred associations. Views, sequences, row-level security, JavaScript-converted defaults, placeholders and unresolved references are diagnostics, never guessed. Several connections map to their own modules (`databases.NAME.modules`, with `driver`), and `drizzle.casing` follows `drizzle({ casing })`. Drizzle 1.0 (relations v2) is refused for now.
- Build configuration in the `"node-schema-viewer"` key of `package.json`: `source`, `orm` (else detected from the dependencies), `modules` (paths, globs or package names), `databases.NAME` (`urlEnv`, `schemas`, `driver`, `modules`), `databaseUrlEnv`, `databaseSchemas`, `databaseConnection`, `isolation`, `timeout`, `containerImage`, the extraction worker settings and `drizzle.casing`, validated strictly (unknown keys, URL values, URL variables passed to the extraction worker and conflicting options are errors that never echo values). `init` takes `--orm` and `--module`.
- The internal schema model carries ORM models, ORM relationships, ORM defaults and per-ORM `extensions`; the serializer writes them, drops inverses that name no relationship, lists equal diagnostics once and computes `inferredAssociations` with the shared `inferAssociations` (empty for database documents, which have no models).
- Tests: the Drizzle adapter per dialect on synthetic schemas (`tests/drizzle.test.ts`), `build` end to end (`tests/build.test.ts`: configuration, exit codes, process isolation on Node.js 26 and its refusal on 22 and 24, container isolation, database builds on PostgreSQL, MySQL, MariaDB and SQLite, credentials, atomic output, a hostile schema module), and the parity of declared and database documents of one schema on all four databases.
- Documentation site (VitePress, `.gh-page/`, deployed to GitHub Pages by `.github/workflows/deploy-docs.yml`): built from `docs/`, with installation, quick start, supported ORMs, multiple connections, architecture, troubleshooting and agent-skills pages, and a live demo of the pinned `laranex-schema-viewer-ui` viewer on synthetic shared fixtures.
- Tests: python-schema-viewer's exit code and stderr for a `*` target that matches no schema, a comparison configured or named twice (`compare` and `check`) and invalid overrides (`scripts/record-python-intel-conformance.py`, now 39 cases, equal apart from the configuration location and `object_type`/`objectType`); the 43 shared request, coverage-gap, override, comparison-diagnostic and store conformance cases; `compare --write` and `check --output` under `--permission` with `--allow-fs-write` limited to the output directory on every tested Node.js version; atomic-write failures (a write failing midway, `fsync` errors, a failed rename, the Permission Model) and the exit codes of `compare --write` (1) and `check --output` (2) when they cannot write.

- `compare [BASELINE=TARGET...] [--snapshot PATH] [--limit N] [--json] [--write]`: schema comparisons of a saved document with the shared `compareScopes` algorithm, without a database, application imports or subprocesses. Scopes are `CONNECTION` or `CONNECTION:SCHEMA` by connection name; a target `CONNECTION:*` expands to every schema the connection's inspection read except the baseline's own scope, and a pair named explicitly wins over the same pair from an expansion. Prints python-schema-viewer's summary, or the comparison objects as canonical JSON (`--json`); `--write` stores them in the document (2.0 only), strictly validated and atomically, replacing comparisons of the same scopes and their diagnostics and keeping the others, with a `comparison_incomplete` diagnostic for each incomplete one. See `docs/comparison.md`.
- `check`, the CI schema drift gate: a thin layer over the shared reference gate (`gateDocument`) that prints a deterministic summary or the canonical `laranex-schema-gate` 1.0 report (`--json`, `--output FILE` written atomically) and exits 0 (passed), 1 (a finding meets the thresholds) or 2 (an invalid or unreadable document, a requested comparison not found, an incomplete comparison or inspection, a failed inspection, an unknown migration status, or invalid arguments or configuration; 2 wins over 1, and no failure exits 0 or 1). Requests are the comparisons named on the command line (computed in memory, then requested), else the configured ones as configured, else every stored one; thresholds come from `--severity`/`--certainty`, the configuration, then the shared defaults (`warning`, `certain`). See `docs/check.md`, with a GitHub Actions example.
- Configuration: `comparisons` (`baseline`, `target`, `limit`, `overrides` with `objectType`, `change`, `field`, `severity`) and `check` (`severity`, `certainty`) in the `"node-schema-viewer"` key of `package.json`, validated as strictly as python-schema-viewer's (unknown keys and values, self-comparisons, `*` baselines and URL-like values are errors that never echo the value).
- MCP `schema_compare`: stored comparisons (section `comparisons`, with scope labels and counts) or their differences (section `differences`, filtered by `object_type`, `change`, `severity`, `certainty`), selected by comparison id or `baseline`/`target` scope, with python-schema-viewer's arguments, annotations, description, envelope, error order and 64 KiB limit. It never computes a comparison.
- Conformance: the 23 shared gate cases through `gateDocument` and end to end through `check --json` (byte-identical reports), the 6 valid and 13 invalid shared gate report fixtures through `validateGateReport`, `compare` and `check` output byte-identical to python-schema-viewer's on four documents it built from synthetic databases (`scripts/record-python-intel-conformance.py`), and `compare`/`check` run under the Permission Model with a network and child-process sentinel.
- The shared contract suite from the installed package: every valid fixture passes strict validation and keeps identical canonical bytes through loading and writing, every invalid fixture is rejected, and the graph, migration, comparison and inference conformance cases pass through the package's `buildGraph`, `migrationHistory`/`migrationState`, `compareScopes` and `inferAssociations`.
- A release guard, `npm run check:release` (also `prepublishOnly`), which fails while any dependency is not an exact version from the npm registry. The packaging test fails when it does.
- Package foundation: TypeScript (strict, ESM), ESLint with typescript-eslint, `node:test` suite compiled with `tsc`, MIT license. Requires Node.js 22.13 or later; tested on 22, 24 and 26.
- Static configuration under `"node-schema-viewer"` in the project's `package.json` (`output`), with unknown keys and database URLs rejected, and `init`, which adds the key without changing anything else.
- laranex-schema 2.x snapshots: bounded loading (32 MiB) with lenient reader validation, canonical JSON and revisions from `laranex-schema-viewer-ui`'s contract, strict validation and atomic writes for everything the package writes.
- `serve`: the shared viewer (`laranex-schema-viewer-ui` 0.3.0: multi-connection frames and cross-connection reference nodes, and its favicon) on `127.0.0.1:8765`, serving only manifest-listed files verified by SHA-256 at startup, `/snapshot.json` re-read and validated on every request, Host checks, GET/HEAD only, and python-schema-viewer's Content-Security-Policy.
- `mcp`: the read-only tools of python-schema-viewer (`schema_overview`, `schema_search`, `schema_get_table`, `schema_get_model`, `schema_get_relationships`, and `schema_compare` above) on the official MCP TypeScript SDK v2, with the same arguments, annotations, descriptions and laranex-schema 2.0 response format (python-schema-viewer's `docs/mcp.md`): the document's contract objects as items, the `revision`/`total`/`offset`/`limit`/`items`/`nextOffset` envelope, a 64 KiB cap on compact UTF-8 JSON with 128 bytes reserved, the `links`, `derived_links` and `diagnostics` table sections, `{table, foreignKey}` foreign-key entries, `{kind, id, table, name}` search hits, and an overview with version, source, generator, note, connections, counts and diagnostic counts. A conformance suite compares all 1,801 calls python-schema-viewer recorded over the 14 shared valid fixtures and two byte-limit documents (including `schema_compare`), by value through the query functions and by response text over stdio with the SDK client (1,633 byte-equal; the other 168 are input-schema rejections, which each SDK words its own way). `unifiedView` and the 1.0 response fields are gone.
- Isolated model extraction for `build` (`src/isolation/`): an extraction worker under the Node.js Permission Model (`--permission`, per-path read and write grants, `--no-addons`, `--no-experimental-sqlite`, `--disallow-code-generation-from-strings` unless `allowCodeGeneration`), with an allowlisted environment that withholds credentials and reports only how many variables it withheld, a private `HOME` and `TMPDIR`, a timeout, process-group cleanup, and a strictly validated result file of at most 32 MiB. `container` isolation runs the same worker in Docker or Podman with no network, a read-only project and root filesystem, all capabilities dropped and no new privileges, after checking the image: it is never pulled unless `pullImage` opts in (with a notice for references not pinned by digest), and its own worker entry point must report this package at the same version (found from the image's working directory or `containerPackagePath`; no global install needed). `NODE_ENV` reaches the worker only unchanged and as a plain token. Process isolation needs Node.js 26 (the first version whose Permission Model blocks network access); on Node.js 22 and 24 it is refused and container isolation is required. Nothing falls back to a weaker level. TypeScript models load through a `module.registerHooks` transpiling hook using the project's `typescript`. See `docs/security.md`.
- Read-only database introspection (`introspect`, `introspectAll`, `merge`, and `build --source database`): PostgreSQL (`pg` 8.23.1), MySQL and MariaDB (`mysql2` 3.24.5) and SQLite (`node:sqlite`) catalogs as a laranex-schema 2.0 `database` document with python-schema-viewer's ids and normalization: schema-qualified tables, columns, defaults, generated columns, enums, collations, comments, composite keys, cross-schema foreign keys with actions and deferral, unique and check constraints, every index feature (expressions, order, nulls, prefixes, collations, operator classes, methods, predicates, included columns, `NULLS NOT DISTINCT`, invisible indexes), coverage per database, and several connections merged into one document. Each connection is read by its own introspection worker, separate from the extraction worker, under the Permission Model (read access to this package and its drivers only, never the project; `--no-addons`; `--disallow-code-generation-from-strings`), with the URL on stdin only, an allowlisted environment, a private `HOME`, scrubbed errors, timeouts with process-group cleanup and a strictly validated result. Sessions are read-only and verified (PostgreSQL and MySQL/MariaDB read-only transactions, SQLite `readOnly` and `query_only`, always rolled back), statements pass a catalog allowlist, and roles that could change the schema or data are refused unless `allowWritePrivileges` is set (then a `write_privileges` diagnostic is recorded). The documents equal python-schema-viewer's for the synthetic test databases. See `docs/database.md` and `docs/security.md`.

### Known issues

- Installing `laranex-schema-viewer-ui` (0.2.0 and 0.3.0) also installs its React, React DOM and `@xyflow/react` peers and dependencies (about 24 MB), which this package does not use at runtime.
- `laranex-schema-viewer-ui`'s type declarations (0.2.0 and 0.3.0) use extensionless relative imports, so TypeScript's `NodeNext` resolution cannot see its contract types; this package compiles with `Bundler` resolution.
- For a document of a later minor with properties its version does not define, the revision differs from python-schema-viewer's: Python hashes the document without the unknown properties, this package hashes it as read. Responses are otherwise identical.
- Search folds case per code point like Python's `str.casefold`; characters added in newer Unicode versions than the Python build knows may fold differently.
- `build --source combined` (reconciling declared and database metadata) is not available yet, and Drizzle is the only ORM adapter. Names Drizzle generates (`getName()`) come from the columns' keys; drizzle-kit renames them for a configured casing, which the adapter does not.
- The introspection worker can reach the network on every Node.js version (unrestricted on 22 and 24, `--allow-net` on 26), and `node:sqlite` ignores the Permission Model; SQLite safety rests on the path check, `readOnly` and `query_only`. A foreign key into a schema that is not inspected makes the document invalid, as in python-schema-viewer.
- Process isolation is best-effort: the Permission Model is not a security boundary, symlinks inside readable directories reach their targets, inherited file descriptors, signals to other processes and `node:vm` are not restricted, and everything in the project (including `.env`) is readable. Use container isolation for untrusted code.
