# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed

- **laranex-schema 2.0 only** (`laranex-schema-viewer-ui` 0.3.0-dev.0). Snapshots are read as 2.x (later minors leniently) and written as strictly validated, canonical 2.0; a 1.x document is refused with one clear error (`Unsupported laranex-schema version "1.0"; this reader supports 2.x. Rebuild the snapshot with a producer that writes laranex-schema 2.0 …`). Nothing converts 1.x.
- Database introspection writes 2.0: canonical driver names (`postgresql` instead of `pgsql`, `mysql`, `mariadb`, `sqlite`), indexes with `parts` and `backs` only (no `Index.columns` or `Index.primary`), diagnostics with rule-based ids, and the new `comparisons`, `migrations` and `inferredAssociations` arrays (empty for now). The catalog readers fill a normalized internal schema model that does not use the document's field names, and one serializer writes it, builds the links with the shared graph builder and validates strictly; `merge` composes serialized documents. The database conformance documents are python-schema-viewer's own 2.0 output, recorded from the same synthetic databases, and the Node.js documents equal them. Security is unchanged: separate worker, Permission Model flags, URL on stdin, verified read-only sessions, privilege checks and scrubbing.
- The extraction worker's result must be exactly a strictly valid 2.0 `declared` document.
- Containers are named `nsv-extract-…` (python-schema-viewer uses `lsv-extract-…`), and a timed-out container is waited for until the runtime has really removed it; the error names it.
- `serve` serves the 0.3.0-dev.0 viewer from the dependency (manifest-only, the same Content-Security-Policy) and refuses a viewer build whose manifest does not declare contract major 2.

### Added

- The shared contract suite from the installed package: every valid fixture passes strict validation and keeps identical canonical bytes through loading and writing, every invalid fixture is rejected, and the graph, migration, comparison and inference conformance cases pass through the package's `buildGraph`, `migrationHistory`/`migrationState`, `compareScopes` and `inferAssociations`.
- A release guard, `npm run check:release` (also `prepublishOnly`), which fails while any dependency is not an exact version from the npm registry. The packaging test reports it as a to-do instead of failing, so local development keeps working while the UI is vendored; publishing is blocked.
- Package foundation: TypeScript (strict, ESM), ESLint with typescript-eslint, `node:test` suite compiled with `tsc`, MIT license. Requires Node.js 22.13 or later; tested on 22, 24 and 26.
- Static configuration under `"node-schema-viewer"` in the project's `package.json` (`output`), with unknown keys and database URLs rejected, and `init`, which adds the key without changing anything else.
- laranex-schema 2.x snapshots: bounded loading (32 MiB) with lenient reader validation, canonical JSON and revisions from `laranex-schema-viewer-ui`'s contract, strict validation and atomic writes for everything the package writes.
- `serve`: the shared viewer (`laranex-schema-viewer-ui` 0.3.0-dev.0, vendored until 0.3.0 is on npm: multi-connection frames and cross-connection reference nodes, and its favicon) on `127.0.0.1:8765`, serving only manifest-listed files verified by SHA-256 at startup, `/snapshot.json` re-read and validated on every request, Host checks, GET/HEAD only, and python-schema-viewer's Content-Security-Policy.
- `mcp`: the five read-only tools of python-schema-viewer (`schema_overview`, `schema_search`, `schema_get_table`, `schema_get_model`, `schema_get_relationships`) on the official MCP TypeScript SDK v2, with the same arguments, annotations, descriptions and laranex-schema 2.0 response format (python-schema-viewer's `docs/mcp.md`): the document's contract objects as items, the `revision`/`total`/`offset`/`limit`/`items`/`nextOffset` envelope, a 64 KiB cap on compact UTF-8 JSON with 128 bytes reserved, the `links`, `derived_links` and `diagnostics` table sections, `{table, foreignKey}` foreign-key entries, `{kind, id, table, name}` search hits, and an overview with version, source, generator, note, connections, counts and diagnostic counts. A conformance suite compares all 1,470 calls python-schema-viewer recorded over the 13 shared valid fixtures and a byte-limit document, by value through the query functions and by response text over stdio with the SDK client (1,405 byte-equal; the other 65 are input-schema rejections, which each SDK words its own way). `unifiedView` and the 1.0 response fields are gone.
- Isolated model extraction for the upcoming `build` (`src/isolation/`, not yet reachable from the CLI): an extraction worker under the Node.js Permission Model (`--permission`, per-path read and write grants, `--no-addons`, `--no-experimental-sqlite`, `--disallow-code-generation-from-strings` unless `allowCodeGeneration`), with an allowlisted environment that withholds credentials and reports only how many variables it withheld, a private `HOME` and `TMPDIR`, a timeout, process-group cleanup, and a strictly validated result file of at most 32 MiB. `container` isolation runs the same worker in Docker or Podman with no network, a read-only project and root filesystem, all capabilities dropped and no new privileges, after checking the image: it is never pulled unless `pullImage` opts in (with a notice for references not pinned by digest), and its own worker entry point must report this package at the same version (found from the image's working directory or `containerPackagePath`; no global install needed). `NODE_ENV` reaches the worker only unchanged and as a plain token. Process isolation needs Node.js 26 (the first version whose Permission Model blocks network access); on Node.js 22 and 24 it is refused and container isolation is required. Nothing falls back to a weaker level. TypeScript models load through a `module.registerHooks` transpiling hook using the project's `typescript`. See `docs/security.md`.
- Read-only database introspection (`introspect`, `introspectAll`, `merge`; no CLI yet): PostgreSQL (`pg` 8.23.1), MySQL and MariaDB (`mysql2` 3.24.5) and SQLite (`node:sqlite`) catalogs as a laranex-schema 2.0 `database` document with python-schema-viewer's ids and normalization: schema-qualified tables, columns, defaults, generated columns, enums, collations, comments, composite keys, cross-schema foreign keys with actions and deferral, unique and check constraints, every index feature (expressions, order, nulls, prefixes, collations, operator classes, methods, predicates, included columns, `NULLS NOT DISTINCT`, invisible indexes), coverage per database, and several connections merged into one document. Each connection is read by its own introspection worker, separate from the extraction worker, under the Permission Model (read access to this package and its drivers only, never the project; `--no-addons`; `--disallow-code-generation-from-strings`), with the URL on stdin only, an allowlisted environment, a private `HOME`, scrubbed errors, timeouts with process-group cleanup and a strictly validated result. Sessions are read-only and verified (PostgreSQL and MySQL/MariaDB read-only transactions, SQLite `readOnly` and `query_only`, always rolled back), statements pass a catalog allowlist, and roles that could change the schema or data are refused unless `allowWritePrivileges` is set (then a `write_privileges` diagnostic is recorded). The documents equal python-schema-viewer's for the synthetic test databases. See `docs/database.md` and `docs/security.md`.

### Known issues

- `laranex-schema-viewer-ui` 0.3.0 is not on npm yet: the dependency is the vendored `vendor/laranex-schema-viewer-ui-0.3.0-dev.0.tgz` (`file:`), so this package cannot be released (the release guard fails). Switch to laranex-schema-viewer-ui 0.3.0 from npm once published, and remove `vendor/`, the `overrides` step in the packaging test and the vendored tarball in the test container image.
- Installing `laranex-schema-viewer-ui` (0.2.0 and 0.3.0-dev.0) also installs its React, React DOM and `@xyflow/react` peers and dependencies (about 24 MB), which this package does not use at runtime.
- `laranex-schema-viewer-ui`'s type declarations (0.2.0 and 0.3.0-dev.0) use extensionless relative imports, so TypeScript's `NodeNext` resolution cannot see its contract types; this package compiles with `Bundler` resolution.
- For a document of a later minor with properties its version does not define, the revision differs from python-schema-viewer's: Python hashes the document without the unknown properties, this package hashes it as read. Responses are otherwise identical.
- Search folds case per code point like Python's `str.casefold`; characters added in newer Unicode versions than the Python build knows may fold differently.
- `build` is not available yet, so introspection is reachable only through the API.
- The introspection worker can reach the network on every Node.js version (unrestricted on 22 and 24, `--allow-net` on 26), and `node:sqlite` ignores the Permission Model; SQLite safety rests on the path check, `readOnly` and `query_only`. A foreign key into a schema that is not inspected makes the document invalid, as in python-schema-viewer.
- Process isolation is best-effort: the Permission Model is not a security boundary, symlinks inside readable directories reach their targets, inherited file descriptors, signals to other processes and `node:vm` are not restricted, and everything in the project (including `.env`) is readable. Use container isolation for untrusted code.
